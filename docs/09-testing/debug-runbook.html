Phương pháp

Bốn quy tắc áp dụng cho mọi tầng. Chúng tồn tại để bạn không sửa nhầm chỗ.

Đọc lỗi đầu tiên Pytest và Vite đều đổ hàng loạt lỗi phái sinh sau lỗi gốc. Lỗi thứ nhất theo thứ tự thời gian là lỗi thật; phần còn lại thường tự biến mất.
Tái hiện thu hẹp Trước khi sửa, chạy lại đúng một test đang fail. Nếu chạy riêng thì pass mà chạy cả bộ thì fail — đó là lỗi cô lập trạng thái, không phải lỗi logic.
Một thay đổi, một lần chạy Sửa hai chỗ rồi chạy lại một lần thì bạn không biết chỗ nào có tác dụng. Giữ nhịp một-đổi-một-chạy cho tới khi xanh.
Sửa code, không sửa test Chỉ nới lỏng assertion khi đã chứng minh được test sai. Trong dự án y tế, một test bảo mật bị nới lỏng là một lỗ hổng được ký duyệt.

Sai đường dẫn Đường dẫn phải trỏ vào src/. Nếu trỏ vào site-packages thì bạn đang test bản đã cài, không phải code đang sửa.
L0.2 Đối chiếu .env với .env.example 1 phút

Mặc định an toàn khi debug là chế độ tất định — không gọi mạng, không tốn API, kết quả lặp lại được:

Giá trị cần có trong app/backend/.env 
HOSPITAL_AI_EMBEDDING_PROVIDER=deterministic
HOSPITAL_AI_CHAT_PROVIDER=stub
HOSPITAL_AI_WORKER_INLINE=false

Nếu lệch
provider=gemini Test sẽ gọi API thật: chậm, tốn tiền, và kết quả đổi mỗi lần chạy nên không debug được. Chỉ bật khi cố ý kiểm thử nhà cung cấp.
Đòi API key Với stub và deterministic thì không cần key. Nếu vẫn báo thiếu, biến môi trường đang bị ghi đè nơi khác — kiểm tra docker-compose.yml, nó set đè thành gemini.

L1 · Đơn vị backend

Tầng này chạy trên SQLite in-memory, không cần Postgres hay Redis. Nếu tầng này đỏ, đừng động đến Docker — lỗi nằm trong logic.

L1.1 Chạy toàn bộ và ghi lại con số Baseline 547 pass
Lệnh 
$ cd app/backend
$ .venv/Scripts/python.exe -m pytest tests/ -q --no-header
Kỳ vọng 
547 passed, 3 skipped, 5 warnings in ~430s
Đọc kết quả
< 547 passed Có test mới fail. Ghi lại tên file rồi sang L1.2 để chạy riêng.
> 3 skipped Test bị bỏ qua ngoài dự kiến, thường do thiếu dependency tuỳ chọn (paddleocr, sentence-transformers). Thêm cờ -rs để xem lý do skip.
Chậm hơn nhiều Guardrails đang chạy thật. conftest.py đặt HOSPITAL_AI_DISABLE_GUARDRAILS=true; nếu bị ghi đè, mỗi lần quét ONNX tốn 4–8 giây.
L1.2 Cô lập test đang fail Vòng lặp chính
Lệnh 
$ .venv/Scripts/python.exe -m pytest tests/test_permissions.py -v
$ .venv/Scripts/python.exe -m pytest tests/test_permissions.py::ten_test -vv --tb=long
$ .venv/Scripts/python.exe -m pytest tests/test_permissions.py::ten_test -x --pdb
Ý nghĩa cờ 
-vv --tb=long   xem đầy đủ giá trị assert, không bị cắt
--pdb           dừng ngay tại chỗ fail, gõ tên biến để soi
-x              dừng ở lỗi đầu tiên
Phân loại lỗi
Riêng pass, chung fail Rò rỉ trạng thái giữa các test, thường do fixture dùng chung session hoặc biến ở cấp module. Thử đảo thứ tự chạy để xác nhận.
Riêng cũng fail Lỗi logic thật. Đây là trường hợp dễ nhất: đọc assert, đặt breakpoint, sửa code nguồn.
Lúc pass lúc fail Lỗi bất định: phụ thuộc thời gian hoặc async race. Chạy lặp nhiều lần để bắt trước khi kết luận.

L2 · Dữ liệu & migration

Từ tầng này trở đi cần dịch vụ ngoài. Bật Postgres và Redis trước khi đi tiếp.

L2.1 Khởi động hạ tầng Cần Docker
Lệnh 
$ docker compose up -d postgres redis
$ docker compose ps
Kỳ vọng 
postgres   healthy   0.0.0.0:5433->5432/tcp
redis      healthy   0.0.0.0:6379->6379/tcp
Cổng Postgres là 5433, không phải 5432

docker-compose.yml map ra 5433, nhưng .env.example ghi localhost:5432. Nếu backend báo connection refused, gần như chắc chắn do chênh lệch này.

L2.2 Migration và seed dữ liệu 16 revisions
Lệnh 
$ .venv/Scripts/python.exe -m alembic current
$ .venv/Scripts/python.exe -m alembic upgrade head
$ .venv/Scripts/python.exe scripts/seed_dev.py
Nếu lỗi
Multiple heads Hai nhánh migration song song. Chạy alembic heads để xem rồi merge. Đừng xoá revision.
type "vector" not exist Đang chạy Postgres thường thay vì image pgvector/pgvector:pg16. Kiểm tra image trong compose.
Duplicate key Đã seed rồi. Bệnh nhân synthetic dùng dải UUID riêng 20000000-…; nếu trùng dải khác là allocator bị đụng.

L3 · API đang chạy

Kiểm tra backend thật qua HTTP. Token dev khai báo trong .env theo cặp token:email.

L3.1 Khởi động và gọi thử Port 8000
Lệnh 
$ .venv/Scripts/python.exe -m uvicorn hospital_ai.main:create_app --reload

# mở tab khác
$ curl http://localhost:8000/api/v1/health
$ curl -H "Authorization: Bearer dev-doctor" \
       http://localhost:8000/api/v1/patients
Token dev có sẵn 
dev-doctor     dev-nurse      dev-pharmacist
dev-records    dev-security   dev-admin
dev-frontdesk
Nếu lỗi
401 Token không khớp HOSPITAL_AI_DEV_BEARER_TOKENS, hoặc server khởi động trước khi bạn sửa .env. Restart uvicorn.
429 Rate limit đang bật — đây là hành vi đúng. Limiter fail-closed, chỉ tắt khi TESTING=true. Đừng tắt nó cho "dễ test".
CORS blocked Frontend chạy port 8082; origin đó phải nằm trong HOSPITAL_AI_CORS_ORIGINS.
L3.2 Kiểm tra hợp đồng API và luồng khói Script có sẵn
Lệnh

$ .venv/Scripts/python.exe scripts/smoke_upload_index_chat.py

Script thứ hai chạy trọn vòng đời tài liệu: upload → OCR → index → hỏi đáp. Đây là bài kiểm tra tích hợp nhanh nhất cho cả pipeline.

L4 · Bảo mật

Tầng quan trọng nhất của dự án. Bốn ràng buộc dưới đây là bất biến — nếu một trong số chúng đỏ, dừng mọi việc khác và sửa trước.

L4.1 Bốn ràng buộc bất biến Không nới lỏng
Lệnh 
$ .venv/Scripts/python.exe -m pytest \
    tests/test_permissions.py \
    tests/test_chat_citations.py \
    tests/test_safe_refusal.py \
    tests/test_auth.py -v
Phải luôn đúng
ABAC nằm trong SQL Lọc quyền bệnh nhân đặt trong mệnh đề WHERE của truy vấn retrieval. Chunk không được phép không bao giờ rời khỏi database, chứ không phải lọc sau khi đã lấy ra.
Citation kiểm hai lần Một lần trong services/reasoning.py, một lần ở biên services/chat.py. Lần thứ hai còn từ chối câu trả lời không có citation nào.
Rate limit fail-closed api/limiter.py luôn bật trừ khi TESTING=true. Không bao giờ đặt mặc định là tắt.
Token không vào localStorage lib/session.tsx chỉ lưu role và workspaceId, ràng buộc bằng satisfies PersistedSession. Token thật chỉ nằm trong bộ nhớ tại lib/api-client.ts.
L4.2 Tự kiểm tra rò rỉ token trên trình duyệt Thủ công
Thao tác 
1. Mở app, đăng nhập bằng tài khoản dev
2. DevTools → Application → Local Storage
3. Đọc giá trị khoá "hms.session"
Kỳ vọng 
{"role":"cardiologist","workspaceId":"ws-cardio-4n"}

Không xuất hiện trường "token".
Đừng nhầm với seam của test E2E

Helper e2e/_helpers.ts có ghi token vào localStorage để dựng phiên giả trước khi app khởi động. Đó là công cụ của test, không phải hành vi ứng dụng. Kiểm tra rò rỉ phải làm thủ công qua luồng đăng nhập thật.

L5 · RAG & AI

Tầng khó debug nhất vì đầu ra không tất định khi dùng LLM thật. Luôn debug ở chế độ stub trước, chỉ đổi sang model thật ở bước cuối.

L5.1 Tách retrieval khỏi generation Nguyên tắc

Câu trả lời sai có đúng hai nguyên nhân, và chúng cần cách sửa hoàn toàn khác nhau. Xác định nguyên nhân trước khi sửa bất cứ thứ gì:

Lấy sai bằng chứng Chunk đúng không nằm trong top-k. Sửa ở embedding, chunking hoặc reranking — không phải ở prompt.
Lấy đúng, trả lời sai Chunk đúng đã có trong ngữ cảnh nhưng model diễn giải sai. Sửa ở prompt hoặc pipeline suy luận.
Lệnh soi 
$ .venv/Scripts/python.exe -m pytest tests/test_retrieval_sql.py -v
$ .venv/Scripts/python.exe -m pytest tests/test_reranking.py -v
$ .venv/Scripts/python.exe -m pytest tests/test_graph_rag_integration.py -v
L5.2 Bẫy top-k của bộ lọc theo vai trò Dễ chẩn đoán nhầm

Lọc theo vai trò chạy bằng Python sau khi LIMIT :top_k đã áp dụng (services/retrieval.py, hàm _apply_role_filters). Hệ quả: kết quả trả về có thể ít hơn top_k, và triệu chứng trông hệt như "retrieval kém".

Cách phân biệt 
Đếm số chunk trước và sau bước lọc vai trò.
Trước đủ, sau thiếu  → vấn đề là top-k, không phải embedding.
Xử lý: tăng top_k, đừng đổi model embedding.

L7 · E2E

Tầng chậm nhất và dễ nhiễu nhất. Chỉ chạy khi L1 đến L6 đã xanh.

L7.1 Chạy Playwright Cần backend chạy sẵn
Lệnh 
$ cd app/frontend
$ bun run test:e2e
$ bun run test:e2e:ui
$ bunx playwright test e2e/rbac-flow.spec.ts --headed
Playwright chỉ tự khởi động frontend

Config tự chạy bun run dev --port 8082 nhưng không khởi động backend. Bạn phải tự chạy uvicorn ở port 8000 trước, nếu không mọi spec gọi API sẽ đỏ hàng loạt.

Đọc lỗi E2E
Fail rồi retry pass Nhiễu do tranh chấp tài nguyên, không phải bug. Config đặt retries: 1 và giới hạn 4 workers vì nút thắt là một backend duy nhất ở port 8000.
Timeout hàng loạt Backend chưa chạy hoặc đã chết. Kiểm tra tab uvicorn trước khi nghi ngờ test.
Redirect /auth/login Phiên giả chưa được seed. Spec phải gọi seedSession(page) từ _helpers.ts trước khi điều hướng.
L7.2 Đọc bằng chứng khi fail Trace viewer
Lệnh 
$ bunx playwright show-trace test-results/<ten-test>/trace.zip

Config đặt trace và video ở chế độ retain-on-failure, nên chỉ test fail mới có artifact. Trace viewer cho bạn xem lại DOM tại từng bước — hữu ích hơn nhiều so với đọc log.
