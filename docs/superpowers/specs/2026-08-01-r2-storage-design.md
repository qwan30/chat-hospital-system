# Phase 2 R2 Storage Design

**Status:** Approved by user on 2026-08-01

## Goal

Add a backend-only storage abstraction that keeps the existing local filesystem backend for tests and local development while supporting Cloudflare R2 through an S3-compatible client. Uploaded documents and rendered page images must be addressed by backend-owned storage URIs, and OCR/workers/API content serving must not assume that a URI is a local filesystem path.

## Architecture

StorageService is a small synchronous read/write protocol plus the existing async save_upload boundary required by FastAPI UploadFile. LocalStorageService preserves absolute local paths returned by the current code so existing tests and local data remain compatible. R2StorageService stores objects in the configured bucket and returns r2://<object-key> URIs.

The API obtains a backend with get_storage_service(settings). API routes read bytes through asyncio.to_thread so the synchronous S3 client does not block the FastAPI event loop. RQ workers and OCR use the same synchronous service directly. R2 keys are generated by the backend and parsed by one allowlisted URI helper.

## Contract

- async save_upload(*, patient_id, document_id, file) -> str
- read_bytes(storage_uri: str) -> bytes
- source_sha256(storage_uri: str) -> str
- save_page_image(patient_id, document_id, page_number, image_bytes) -> str
- read_page_image(patient_id, document_id, page_number) -> bytes

The contract returns bytes for serving and OCR. It does not expose filesystem paths, R2 clients, credentials, signed URLs, or bucket metadata to the frontend.

## Configuration

HOSPITAL_AI_STORAGE_BACKEND=local|r2
HOSPITAL_AI_R2_ENDPOINT=
HOSPITAL_AI_R2_BUCKET=
HOSPITAL_AI_R2_REGION=auto
HOSPITAL_AI_R2_ACCESS_KEY_ID=
HOSPITAL_AI_R2_SECRET_ACCESS_KEY=

R2 mode fails fast when endpoint, bucket, access key, or secret key is absent. Credentials are never placed in frontend VITE_* variables, response models, logs, or error messages.

## Object keys and URI rules

Original uploads use patients/{patient_id}/documents/{document_id}/{sanitized_filename}. Page PNGs use patients/{patient_id}/documents/{document_id}/pages/{page_number}.png. The database value is r2:// followed by the object key; the bucket is selected only from backend settings.

Parsing rejects empty keys, backslashes, dot/dot-dot segments, absolute keys, query strings, fragments, and non-r2 URIs. Existing local path documents remain readable through the local backend with root validation.

## OCR and API flow

1. Upload route selects the backend and stores the original file.
2. Worker selects the same backend, computes source SHA-256 from object bytes, and passes the bytes-backed service to OcrService.
3. Text documents decode bytes; PDFs/images open from bytes with PyMuPDF.
4. Each rendered PNG is written through save_page_image.
5. Content and page-image routes authorize first, then return Response bytes with the database MIME type or image/png.

Virtual hms:// documents keep their existing database-page behavior and are not sent to R2.

## Verification and non-goals

Tests cover local regression, factory selection, mocked R2 upload/read, page PNG round-trip, SHA-256, worker processing of r2://, URI traversal rejection, content serving, and frontend credential isolation. This phase does not deploy infrastructure, create R2 buckets, add migrations, add frontend R2 SDK code, or implement presigned direct-to-browser uploads.
