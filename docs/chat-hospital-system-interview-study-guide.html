Interview Method

Công thức trả lời để “ăn điểm”

Không cần học thuộc từng chữ. Hãy trả lời theo một cấu trúc ổn định để interviewer thấy bạn có tư duy hệ thống, biết trade-off và không “overclaim”.

1 · Context
Bối cảnh

Vấn đề gì đang được giải quyết? Constraint nào quan trọng: healthcare, PHI, latency, scale, audit?

2 · Decision
Quyết định

Bạn chọn giải pháp nào và vì sao? Nêu một lựa chọn thay thế để chứng minh bạn hiểu trade-off.

3 · Execution
Cách chạy

Đi end-to-end qua flow thực tế, chỉ rõ điểm enforce permission, transaction, retry, validation.

4 · Evidence
Kết quả & giới hạn

Nêu metric/test/trace. Nếu prototype chưa production-grade, nói rõ và đề xuất bước tiếp theo.

Gợi ý dùng trong phỏng vấn: với câu hỏi hành vi dùng STAR; với câu kỹ thuật dùng Context → Decision → Trade-off → Failure mode → Validation. Một câu trả lời senior thường có ít nhất một câu kiểu: “Cách hiện tại hoạt động ở scope portfolio, nhưng để production tôi sẽ thêm…”.

01 · Architecture

Project story & system design

Đây là nơi interviewer xác minh bạn có thật sự làm project và hiểu toàn hệ thống hay chỉ biết README.

Câu trả lời mẫu

“Project của em là một AI Hospital Knowledge Assistant hỗ trợ nhân viên y tế truy vấn thông tin bệnh nhân và tài liệu lâm sàng bằng RAG. Điểm em tập trung không chỉ là chatbot mà là security boundary của RAG trong healthcare: trước retrieval hệ thống kiểm tra quyền truy cập bệnh nhân; sau đó mới retrieve evidence, tạo câu trả lời grounded và validate citation trước khi trả về client.

Backend dùng FastAPI, PostgreSQL + pgvector để kết hợp relational data và vector search, Redis/RQ cho document processing background jobs, frontend dùng TanStack Start và SSE cho streaming. Ngoài luồng RAG, hệ thống có OCR/indexing pipeline, Knowledge Graph và CDSS worker để phát hiện rủi ro từ tài liệu mới.

Phần em muốn highlight nhất là thiết kế permission-aware retrieval, hybrid search, citation validation và cách em cân bằng giữa latency với safety trong streaming.”

Điểm interviewer đang đánh giá

  • Bạn có nói rõ problem → solution → architecture → contribution.
  • Bạn có biết đâu là “USP” thay vì liệt kê tech stack.
  • Bạn có chủ động dẫn interviewer vào phần mình hiểu sâu nhất.

Cách trả lời ăn điểm

Không nói “em làm tất cả” nếu không đúng. Chia thành 3 tầng:

  • Owned: phần bạn trực tiếp thiết kế và code.
  • Integrated: phần bạn kết nối / cấu hình / mở rộng.
  • Prototype: phần còn giới hạn và bạn biết rõ limitation.

Ví dụ: “Em trực tiếp thiết kế luồng RAG, permission check trước retrieval, retrieval service, citation validation và trace/debugging. OCR worker và CDSS em tích hợp trên cùng pipeline, còn phần clinical validation hiện mới ở mức prototype nên em không coi nó là production medical decision system.”

Tránh

“Em làm full hết từ A–Z.” Nếu interviewer mở code và hỏi sâu từng module, câu này dễ phản tác dụng.

1. Frontend gửi query + patient context.
2. FastAPI xác thực JWT → lấy current user.
3. Permission service kiểm tra user có quyền với patient và scope tương ứng hay không.
4. Nếu pass, hệ thống tạo query embedding.
5. Retrieval chạy trong patient scope, sau đó role/document-level filtering.
6. Hybrid retrieval có thể kết hợp vector + BM25 bằng RRF.
7. Top-K evidence được chuẩn hóa thành context.
8. Nếu evidence dưới threshold → từ chối / trả no-evidence.
9. LLM sinh answer có citation IDs.
10. Citation validator kiểm tra ID có thuộc retrieved evidence không.
11. Persist AI query, evidence, audit/trace.
12. Trả response về client; với RAG an toàn hơn thì buffer trước khi emit final.

Câu trả lời mẫu

“Em chọn hybrid Clean/Pipeline vì domain hiện tập trung nhiều vào các luồng xử lý tuần tự — document ingestion, retrieval, generation, validation — nên pipeline rõ hơn việc ép mọi thứ thành aggregate/domain service. Em vẫn giữ separation: API layer chỉ nhận request, service layer điều phối, DB layer persistence, provider abstraction cho LLM/embedding.

Trade-off là dependency rule không được enforce mạnh như hexagonal/clean thuần. Nếu team lớn hơn, em sẽ thêm boundary test hoặc import-linter để ngăn core/service phụ thuộc ngược vào FastAPI hoặc infrastructure.”

Câu trả lời mẫu

“Ở quy mô hiện tại, PostgreSQL + pgvector giúp em đặt relational data, permission metadata và vector cùng một consistency boundary. Em có thể filter theo patient/document/status gần data, giảm operational complexity và không phải đồng bộ thêm một distributed vector system.

Dedicated vector DB sẽ hợp lý hơn khi vector volume hoặc QPS lớn, cần distributed ANN, sharding chuyên dụng hoặc advanced retrieval features. Lúc đó em sẽ đánh đổi sự đơn giản hiện tại để lấy scalability.”

Follow-up nên chủ động nói

  • HNSW index cần memory.
  • Filter + ANN có thể ảnh hưởng recall/performance.
  • Scale lớn cần partitioning, read replica hoặc tách vector tier.
02 · RAG

Retrieval, ranking, embedding & grounding

Đây thường là phần bị hỏi sâu nhất nếu bạn apply AI Engineer hoặc Backend có AI.

Query
→ Auth + patient permission
→ Query embedding
→ Patient-scoped retrieval
→ BM25 / Vector / Hybrid
→ RRF fusion
→ Role / document filtering
→ Top-K + threshold
→ Context construction
→ LLM generation
→ Citation ID extraction
→ Citation allow-list validation
→ Persist trace/evidence/audit
→ Final response

Câu trả lời mẫu

“Vector search tốt với truy vấn semantic, nhưng healthcare có nhiều token chính xác như mã thuốc, lab values, ICD codes, đơn vị đo. BM25 mạnh ở exact lexical match. Vì vậy hybrid search giúp tận dụng cả semantic recall và lexical precision.

Ví dụ ‘BNP 1250 pg/mL’ phù hợp BM25, còn ‘patient có dấu hiệu heart failure không?’ phù hợp semantic search. Em fuse ranking bằng Reciprocal Rank Fusion vì nó không yêu cầu score của hai retriever phải cùng scale.”

Ý chính

RRF xếp hạng theo vị trí rank thay vì phụ thuộc raw score. Với mỗi document, điểm được cộng theo dạng 1 / (k + rank) từ mỗi retriever. Điều này hữu ích vì cosine similarity và BM25 score không cùng scale.

Điểm yếu: RRF bỏ qua magnitude thật của score. Nếu cần tối ưu sâu hơn, có thể học weight, normalize score hoặc dùng reranker cross-encoder.

Trade-off

  • K nhỏ: recall thấp, thiếu context quan trọng.
  • K lớn: tăng token cost, noise, lost-in-the-middle, LLM dễ bị distraction.

Cách trả lời senior

“Em không chọn K cố định chỉ bằng trực giác. Em tune bằng retrieval recall@K, answer faithfulness, latency và token cost trên evaluation set. Có thể retrieve rộng hơn rồi rerank xuống context nhỏ hơn.”

Câu trả lời mẫu

“Chunking cần phụ thuộc document type. Với narrative note có thể dùng token/semantic chunk có overlap; với bảng lab hoặc medication list nên ưu tiên structure-aware chunk để tránh tách hàng/cột có quan hệ. Mục tiêu là một chunk đủ tự-contained để retrieve được nhưng không quá lớn làm giảm precision.

Em sẽ version chunking strategy cùng embedding model, vì thay chunking thường yêu cầu re-index.”

Câu trả lời mẫu

“Vector dimension là một phần của schema/index contract. Đổi model khác dimension thì không thể chỉ switch config. Em cần tạo vector column/index mới hoặc migration, chạy re-embedding toàn bộ corpus, version embedding model trên từng chunk và rebuild ANN index.

Nếu cần zero downtime, em dùng dual-write/dual-index: tạo generation mới, backfill, đánh dấu ready rồi atomically switch retrieval sang generation mới; sau đó mới retire index cũ.”

03 · Security

Permission-aware RAG & PHI boundaries

Trong healthcare, câu hỏi security thường được đánh giá nặng hơn việc “AI trả lời hay”.

Layer 1 — Authentication
JWT → current user

Layer 2 — Patient-level ABAC
user_id + patient_id + permission scope + expires_at

Layer 3 — Retrieval scope
chỉ retrieve trong patient/document scope được phép

Layer 4 — Role/document filtering
Doctor / Nurse / Pharmacist có evidence visibility khác nhau

Layer 5 — Citation allow-list
LLM chỉ được cite evidence đã retrieve hợp lệ

Layer 6 — Audit
trace query → evidence → model → response

RBAC

Quyền dựa trên role: Doctor, Nurse, Pharmacist, Admin… Phù hợp để định nghĩa capability chung.

ABAC

Quyền dựa trên attribute/context: user_id, patient_id, scope, document type, access tags, expires_at. Phù hợp với quyền truy cập theo bệnh nhân và thời hạn.

Câu trả lời tốt

“Tốt nhất enforce coarse permission càng gần data càng tốt: patient scope và hard access boundary nên đi vào retrieval query/filter trước khi candidate evidence rời data layer. Role-specific presentation filtering có thể ở bước sau, nhưng dữ liệu user hoàn toàn không được phép truy cập thì không nên trở thành candidate.

Nếu retrieve toàn index rồi filter trong application memory, dù cuối cùng không show cho user, hệ thống đã mở rộng blast radius: logs, traces, cache hoặc bug có thể làm lộ evidence. Vì vậy em coi pre-filter là security control, post-filter chỉ là defense-in-depth.”

Cách trả lời trung thực mà vẫn ăn điểm

“Hiện implementation đang check permission ở orchestration layer trước retrieval, còn SQL retrieval filter theo patient/document state. Vì vậy access control vẫn có lớp bảo vệ, nhưng claim ‘permission enforced at SQL JOIN level’ trong README đang mạnh hơn implementation hiện tại.

Em sẽ sửa theo hai hướng: hoặc cập nhật tài liệu cho đúng boundary hiện có, hoặc tốt hơn là đưa hard permission predicate vào retrieval SQL/view/RLS để giảm khả năng bypass. Em ưu tiên source of truth là code + tests, README phải phản ánh đúng.”

Câu trả lời mẫu

“Provider abstraction cho phép nhiều provider, nhưng production policy không nên chỉ dựa vào convention. Em sẽ enforce bằng environment allow-list, deployment guardrail, secret/config policy, network egress restriction và audit log. Nếu external provider được phép, cần data processing agreement phù hợp, PHI minimization/redaction và policy rõ ràng theo environment.

Nói cách khác, ‘local-first’ phải là một deployment invariant chứ không chỉ là một comment trong README.”

04 · Backend & Database

Async workers, failure modes & data modeling

Những câu này thường xuất hiện nếu bạn apply Backend Engineer hoặc Fullstack thiên backend.

Câu trả lời mẫu

“Document OCR/indexing là background job pattern tương đối đơn giản: enqueue, retry, status. RQ giúp stack nhẹ vì đã có Redis, setup nhỏ và phù hợp portfolio/scope hiện tại.

Nếu cần routing phức tạp, scheduled workflows, rate limit mạnh hoặc distributed retry policy, Celery hợp hơn. Nếu cần event streaming, replay, consumer groups và decoupled domain events ở quy mô lớn, Kafka phù hợp hơn nhưng operational cost cao hơn.”

Khung trả lời

  • Document có state machine: uploaded → processing → indexed hoặc failed.
  • Job retry phải an toàn: cùng source SHA / generation không tạo duplicate chunk.
  • Chunk/embedding write dùng unique key theo document + generation + chunk index.
  • Chỉ mark indexed sau khi toàn bộ transaction/index generation hoàn tất.
  • Dead-letter/manual retry cho job fail nhiều lần.

Lợi ích

Filter patient trực tiếp trên bảng vector, giảm JOIN trong hot retrieval path, thuận lợi cho ANN pre-filter.

Chi phí

Duplicate data và consistency risk. Cần enforce bằng FK/trigger/application invariant hoặc coi chunk immutable theo document generation.

Câu trả lời ngắn gọn nhưng sâu

UUID phù hợp khi ID cần generate phân tán hoặc khó đoán, nhưng UUID v4 random gây locality kém hơn bigint trên B-tree. Bigint nhỏ, nhanh, cache-friendly nhưng centralized sequence và dễ enumerate. UUID v7 giữ tính globally unique nhưng có time ordering tốt hơn, giảm page split so với v4.

Ý chính

Hot retrieval phải loại document/chunk deleted. Historical audit có thể giữ immutable reference/metadata tùy policy nhưng nội dung PHI có thể phải purge theo retention/right-to-erasure. Chat cũ nên giữ citation tombstone hoặc immutable evidence snapshot theo policy, tránh link đến dữ liệu đã biến mất mà không giải thích.

05 · AI Safety

Citation validation, streaming & CDSS

Đây là nơi một senior interviewer có thể “đánh” mạnh nhất vì project liên quan healthcare.

Hiện tại thường chỉ chứng minh

LLM cite [E1] và E1 thuộc allow-list evidence đã retrieve.

Chưa chứng minh

Claim mà LLM viết thực sự được E1 support về mặt ngữ nghĩa.

Cách nâng cấp

Claim segmentation → citation span mapping → NLI/LLM entailment check → confidence threshold → refuse/flag nếu unsupported. Đây là khác biệt giữa citation existence validation và semantic grounding validation.

Câu trả lời mẫu

“True token streaming tối ưu time-to-first-token nhưng token đã gửi thì không thể thu hồi. Với healthcare, nếu cần validate citation trước khi user thấy nội dung, em chấp nhận buffer final answer như một safety gate. Đây là trade-off có chủ ý: safety cao hơn perceived latency.

Nếu muốn cải thiện, có thể buffer theo sentence/claim, dùng structured generation hoặc two-stage draft → validate → stream.”

Câu trả lời ăn điểm nhất là không overclaim

“Không, implementation hiện tại nên được coi là prototype/decision-support demo, không phải medical device. LLM có thể hallucinate hoặc bỏ sót nên không nên là source of truth cho alert severity.

Production architecture nên dùng deterministic rule engine + trusted drug interaction/clinical knowledge base + Knowledge Graph, còn LLM chủ yếu giải thích, tóm tắt hoặc đề xuất để clinician review. Cần human-in-the-loop, threshold, audit, clinical evaluation, false-positive/false-negative analysis và regulatory process.”

Câu trả lời mẫu

“Em tách detection khỏi explanation. High-risk rule nên dựa trên deterministic/verified sources. LLM output chỉ trở thành suggestion, không trực tiếp actionable. Với alert quan trọng, cần evidence trace, confidence, source provenance và clinician confirmation. Đồng thời đo cả precision lẫn recall vì healthcare không thể chỉ tối ưu một phía.”

06 · Testing & Operations

RAG evaluation, observability & scale

Một câu trả lời tốt không dừng ở “có 250+ tests”; interviewer muốn biết test gì là quan trọng.

Câu trả lời mẫu

“Em tách test theo layer. Retrieval test đo recall@K/precision@K trên golden set; permission test đảm bảo cross-patient leakage bằng 0; citation test kiểm tra allow-list; generation test assert cấu trúc, refusal/no-evidence behavior và grounded claims thay vì exact sentence. E2E chỉ giữ một số scenario quan trọng để tránh flaky.”

Câu trả lời gợi ý

“Test quan trọng nhất với em không phải endpoint trả 200, mà là invariant: User A không bao giờ retrieve evidence của Patient B nếu không có permission. Em muốn test ở cả service layer và integration DB layer để tránh bypass do refactor.”

trace_id
→ user / patient permission
→ normalized query
→ embedding model + version
→ retrieved chunks
→ vector/BM25 rank
→ rerank/fusion score
→ top-K evidence
→ context sent to model
→ model + prompt version
→ raw output
→ citations
→ validation result
→ persisted response / latency

Các bước trả lời nên theo thứ tự

  • Đo trước: query latency, HNSW recall, memory, filter selectivity.
  • Partition theo tenant/patient/document domain nếu hợp lý.
  • Tune HNSW params và reduce candidate set bằng metadata pre-filter.
  • Read replica / scale-up memory.
  • Archive cold corpus.
  • Khi operational limit vượt ngưỡng, tách sang dedicated vector database.

Câu trả lời mẫu

“Source of truth cho runtime phải là lockfile/pyproject/package config và code đang deploy. README là documentation và có thể drift. Em sẽ sửa mismatch ngay, thêm CI check cho version badges nếu cần, và tách architecture docs thành ADR/versioned docs để giảm stale documentation.”
